## Part 2: Everything we used, explained

### 2.1 The big picture in three sentences

Documents are uploaded to cloud storage, automatically cut into chunks, turned into vectors and stored in a vector database (**ingestion**). When a user asks a question, a safety filter checks it, an AI planner decides what to do, the most relevant chunks are found and re-ordered, and an LLM writes a short answer only from those chunks (**question answering**). A separate evaluation harness measures how good, safe and robust all of this is (**evaluation**).

### 2.2 Application layer (the code)

| Component | What it is | Why we used it | Where |
|---|---|---|---|
| **Python 3.11** | Language | Every AI library we need is Python-first | everywhere |
| **FastAPI** | Web framework for APIs | Fast, typed request models, auto-generated `/docs` page | `app/main.py` (`POST /query`) |
| **Streamlit** | Python UI framework | A chat UI in about 100 lines, no front-end code | `ui/app.py` |
| **LangGraph** | Framework for agent workflows as graphs of nodes | The planner → retriever → responder flow with a conditional branch is exactly a graph. It also gives built-in memory (checkpointing) | `app/agents/graph.py` |
| **LangChain** | LLM integration library | One interface for Groq, Vertex AI and Gemini, and `with_fallbacks()` for the gateway | `app/gateway/llm.py` |
| **Pydantic** | Data validation | Request/response schemas, settings | `app/main.py` |
| **Logfire** | Structured logging/tracing | Nested spans with timings, which produce the readable trace in Part 1 | all nodes |

### 2.3 The agent: three nodes (steps ⑨–⑫)

**What "agentic" means here:** the system doesn't run a fixed pipeline. An LLM (the planner) first decides *what to do* with the message, then the graph routes accordingly.

| Node | Job | Detail |
|---|---|---|
| **Planner** (`app/agents/nodes/planner.py`) | Classifies the message and rewrites it into a good search query | Output is either `CONVERSATIONAL` (small talk → skip retrieval) or a search term. That's why the log shows "Intent identified: how to start Redis in Kubernetes…" instead of the raw question. |
| **Retriever** (`app/agents/nodes/retriever.py`) | Finds evidence | Embeds the search term, gets the top 15 chunks from Qdrant, then reranks to the best 5 |
| **Responder** (`app/agents/nodes/responder.py`) | Writes the answer | **Grounded prompt:** answer only from the five chunks, keep it concise, and if they don't contain the answer reply exactly *"The provided documentation does not cover this."* |

**Memory:** LangGraph saves the conversation state after every step, keyed by `thread_id`, in **Cloud SQL PostgreSQL** (`PostgresSaver`). Follow-up questions ("what about CronJobs?") therefore work, and memory survives restarts.

### 2.4 Retrieval stack (steps ④, ⑤, ⑩, ⑪)

| Component | What it is | Why |
|---|---|---|
| **Chunking** (`app/ingestion/chunking/splitter.py`) | Cuts documents into pieces of ≤1,500 characters with 200 characters of overlap, breaking at line boundaries | An LLM can't read whole manuals per question. Overlap keeps a sentence that crosses a boundary in both chunks, and line-aware splitting keeps code blocks and YAML intact. |
| **Vertex AI `text-embedding-004`** | Google's embedding model: text → 768 numbers | Texts with similar meaning get nearby vectors, so search works by meaning, not keywords. It's on GCP, so it's billed to credits with no extra account. |
| **Qdrant Cloud** | Vector database | Stores vectors and payloads and finds the nearest neighbours by **cosine similarity** using an **HNSW** graph index (fast approximate search). Its free tier is enough, and it's simpler than Vertex AI Vector Search, which bills for an always-on endpoint. |
| **FlashRank (ms-marco-TinyBERT)** | Cross-encoder reranker running on CPU inside the backend | The embedding search compares the query and chunk *separately*. A cross-encoder reads them *together* and scores relevance more precisely. It's small (3 MB) and needs no GPU or API. |
| **Deterministic point IDs** | `uuid5(file path + chunk index)` | If Eventarc delivers the same upload twice, the chunks are overwritten, not duplicated |

**Finding to mention:** with 50× more unrelated documents (78 → 3,978 chunks), the correct document was still in the top 5 for every question. The reranker made a significant difference at only one noise level.

### 2.5 Safety: the guardrail gate (step ⑧)

| Mode | How it works | Result (in-house set) |
|---|---|---|
| **NeMo Guardrails, embeddings-only** *(deployed)* | NVIDIA's guardrail framework. Rules in **Colang** list example jailbreak and off-topic messages. A new message is embedded (FastEmbed) and compared with the examples, and above 0.5 similarity it's blocked with a fixed reply. **No LLM call**, so it's about 80–100 ms and free. | 45% of attacks blocked, 0 false blocks |
| **Llama Prompt Guard 2 (86M)** | Meta's small classifier trained to detect prompt injection, served on Groq | 73% of jailbreaks, 0% off-topic (it isn't trained for scope) |
| **Layered** | Embedding rails, then Prompt Guard | 55% of attacks, 0 false blocks |
| **gpt-oss-safeguard-20b** | An LLM that reads our written policy and labels each message ALLOW / JAILBREAK / OFF_TOPIC | 100% of attacks, 0 false blocks, but ~21 s per check on the free tier |

Code: `app/guardrails/rails.py` (modes) and `app/guardrails/colang_rules.py` (rules).

**Honest finding:** on 200 prompts from the public deepset benchmark, no mode recognised more than 30% of injections *as attacks*.

- The LLM classifier blocked 97% of injections, but almost all of them as "off-topic". It also refused 97% of the benign prompts, which are unrelated to Kubernetes.
- Strict scope enforcement stops most injections against a single-domain assistant. But an injection phrased as a Kubernetes question would pass every mode.
- Input filtering alone isn't a complete defence. The grounded prompt is the second layer.

### 2.6 The LLM gateway (used in steps ⑨ and ⑫)

**What it is:** a function (`app/gateway/llm.py`) that every agent node calls instead of calling a model directly. It holds an ordered list of models and moves to the next one when a call fails or times out (LangChain `with_fallbacks`).

| Order | Deployed version (Phase 3) | Experiment version (Phase 4 branch) |
|---|---|---|
| 1 | Groq gpt-oss-120b | **Vertex AI gpt-oss-120b** (20 s timeout) |
| 2 | Groq qwen3 → gpt-oss-20b (each has its own free quota) | Groq gpt-oss-120b → qwen3 → gpt-oss-20b |
| 3 | Gemini 3.5 Flash-Lite on Vertex AI | Gemini 3.5 Flash-Lite on Vertex AI |

**Why:**

- Groq's free tier has per-minute and daily limits.
- Any single provider can be slow or down.
- The gateway records *which* model answered, so the fallback rate is a measured number.

**Why gpt-oss-120b:** an open-weights 120B model from OpenAI, available on both Groq (free, very fast) and Vertex AI (billed to credits). It's the *same* model on two providers, so a fallback doesn't change answer style.

**Why "in-process" rather than a gateway product (Portkey, LiteLLM proxy):** it needs no extra service, no extra account and has no extra latency hop. Review 1 planned Portkey; we simplified.

### 2.7 Google Cloud services (infrastructure)

| Service | What it does for us | Config |
|---|---|---|
| **Cloud Run** (×3) | Runs our Docker containers: `enterprise-rag-ui`, `enterprise-rag-backend`, `enterprise-rag-ingestion`. Serverless: no VMs to manage, HTTPS for free, **scales to zero** when idle, so idle costs nothing. | 1 vCPU, 2 GiB each; capped max instances |
| **Cloud Storage** (2 buckets) | `raw` bucket receives uploads; `processed` keeps extracted text | — |
| **Eventarc** | Watches the raw bucket. On "object finalized" it calls the ingestion service, which makes ingestion event-driven. | trigger in `terraform/ingestion.tf` |
| **Cloud SQL (PostgreSQL 15)** | Chat memory (LangGraph checkpoints) | `db-f1-micro`, the smallest tier and the main fixed cost |
| **Vertex AI** | Embeddings (`text-embedding-004`), Gemini fallback, and the gpt-oss-120b endpoint | pay-per-token from credits |
| **Secret Manager** | Stores API keys (Groq, Qdrant, DB password); Cloud Run reads them at start-up | nothing secret in code or images |
| **Artifact Registry** | Stores our Docker images | — |
| **Cloud Build** | Builds the images from the repo (`cloudbuild.yaml`) | — |
| **IAM service accounts** (×3) | Each service has its own identity with only the roles it needs (least privilege) | `terraform/main.tf` |
| **Cloud Logging** | Collects all container logs, which is the trace in Part 1 | automatic |

Not used, by design: **Memorystore Redis** (the semantic cache) is written in Terraform but switched off (`enable_redis = false`) because it costs money every hour even when idle. **Document AI** is optional for scanned PDFs; the default is the free `pypdf` parser.

### 2.8 Infrastructure as Code: Terraform

**What it is:** a tool where you *describe* the infrastructure in `.tf` files and Terraform creates, updates or deletes the real resources to match.

**Why it matters:**

- The whole GCP setup (about 30 resources) is reproducible with `terraform apply`.
- It's reviewable in Git and can be torn down with `terraform destroy`.
- `terraform plan` showing "No changes" proves the live system matches the code.

| File | Contents |
|---|---|
| `provider.tf` | Google providers |
| `variables.tf`, `terraform.tfvars` | Settings (tfvars is git-ignored, since it holds keys) |
| `main.tf` | APIs, service accounts, IAM, Artifact Registry, optional Redis/VPC |
| `secrets.tf` | Secret Manager |
| `database.tf` | Cloud SQL |
| `cloud_run.tf` | UI and backend services |
| `ingestion.tf` | Ingestion service, buckets, Eventarc trigger |
| `output.tf` | Prints the URLs |

### 2.9 Evaluation stack (step ⑭)

| Component | What it is | Why |
|---|---|---|
| **RAGAS** | Library that scores RAG answers with an LLM judge | Industry-standard RAG metrics |
| **Gemini 3.5 Flash-Lite** | The judge model | Cheap, fast, on Vertex AI credits |
| **Golden set** (`evals/datasets/rag_golden.json`) | 24 questions with reference answers: 21 answerable, 3 out of scope | Fixed test, so runs are comparable |
| **Guardrail sets** | 36 in-house inputs, plus 200 from the public deepset prompt-injections dataset | In-house and independent attacks |
| **Bootstrap confidence intervals** | Resample the questions 2,000 times to get a 95% range | With 24 questions a single average can mislead; the interval shows how sure we are |
| **Separate virtual env** (`.venv-evals`) | RAGAS has conflicting library versions | Keeps the production app's dependencies clean |

**Metrics in one line each:**

| Metric | What it measures |
|---|---|
| Faithfulness | Is every claim in the answer supported by the retrieved chunks? (catches hallucination) |
| Answer correctness | Does the answer match the reference answer? |
| Answer relevancy | Does it actually address the question? |
| Context precision | Are the retrieved chunks relevant, and ranked well? |
| Context recall | Did retrieval find all the information needed? |
| Hit@5 *(no judge)* | Was the right source document among the five chunks given to the model? |
| Noise intrusion *(no judge)* | What fraction of those five chunks came from unrelated documents? |
| Guardrail recall / false-block rate | Attacks blocked, and legitimate questions wrongly blocked |

### 2.10 Headline numbers

| Experiment | Result |
|---|---|
| Grounded vs original prompt | Faithfulness 0.38 → **0.92**; correctness 0.41 → **0.76**; out-of-scope declined 1/3 → **3/3** |
| Noise 0× → 50× (78 → 3,978 chunks) | Hit@5 **1.00 at every level**; correctness stays 0.68–0.75 |
| Reranker | Significant gain only at 1× noise (+0.22) |
| Guardrails, in-house | Layered 55% blocked, 0 false blocks; LLM classifier 100%, 0 false blocks, but slow |
| Guardrails, external benchmark | No mode recognises more than 30% of injections as attacks; the LLM classifier blocks 97%, mostly as off-topic |
| Reliability | 0 failed questions across all runs; the gateway absorbed provider slowdowns |
| Live latency | About 3 s per answer (trace in Part 1.3) |
